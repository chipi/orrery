# ADR-096 — Indexable entity pages and the SEO surface

> Status · Accepted · 2026-11-09 (operator; amended with decisions 8–12) · 0.9.8 plan item 0 (operator, 2026-11-08) · evidence in
> `docs/wip/2026-11-08-seo-review/` · builds on **ADR-034** (prerender, server-only loads) and the
> `#519` hreflang work · the `/c/*` share stubs of the collectible cards stay as they are

## Context

The 2026-11-08 SEO audit of the build found that search engines could rank almost none of what
Orrery knows. Every mission, vehicle, landing site, body and Lab calculator lived only in a
client-side panel (`/missions?id=`, `/fleet?id=`, `/moon?site=`, `/explore?id=`, the `/lab`
picker); those URLs canonicalise to their hub, so the entity text never reached prerendered HTML.
The only per-entity pages were the 523 `/c/*` card stubs — en-US, noindex, redirecting. Around
that: no Open Graph or JSON-LD on any page, 476 pages without a description, 42 titled just
"Orrery", a 7 MB single-file sitemap, and the GitHub Pages staging mirror outranking the real site
for "porkchop plot calculator" despite its canonical tags.

## Decision

1. **One indexable page per entity, in every locale,** prerendered from the data and overlays the
   panels already use — no new text, the panels' own label messages:
   `/missions/<id>` (126), `/fleet/<id>` (294), `/moon|mars|venus/<site>` (58),
   `/explore/<body>` (48: planets, moons, small bodies), `/lab/<formula>` (65). × 14 locales =
   8,302 pages. Each has H1, facts, the long text, links between entities (mission ↔ vehicle ↔
   site), and an "Open in Orrery" link to the in-app view. The in-app panels stay the app; the
   pages are what search engines and shared links land on.
2. **Server-only loads** (`+page.server.ts`) for every entity route: the JSON they read stays out of
   client JS (a universal load put `/fleet/[id]` at 51 KB against its 30 KB route budget), and
   loaders take the prerender `fetch` (`getFleet`, `getSiteStory`, new `getSiteEntity`,
   `getBodyEntity`). The Lab formula ids are mirrored in `static/data/lab-formulas.json` because
   `scripts/site-routes.mjs` (plain Node) cannot import the TS registry; a test pins it to
   `REGISTRY`.
3. **One route list** — `scripts/site-routes.mjs` seeds the per-locale prerender and the sitemaps,
   so neither can drift. Sitemaps: `/sitemap.xml` is an index of 14 `/sitemaps/<locale>.xml`. Each
   URL carries a truthful `<lastmod>` from the committed `src/lib/generated/route-lastmod.json`
   (`npm run route-lastmod`, run in the release PR on a full-history checkout): the date git last
   changed the files that page is built from. It cannot be computed in the build: CI is a depth-1
   checkout and `.git` is not in the Docker context, so every date would be the build commit's. A
   route missing from the manifest gets no `<lastmod>`.
4. **Head tags from one place each.** `metaDescription()` (≤160, sentence cut) and `pageTitle()`
   (≤60, "Topic — subtitle" keeps the topic) in `$lib/seo`; Open Graph + Twitter tags are added to
   every page by `addSocialMeta()` in the prerender hook from the page's own title, description and
   canonical (a page's own `og:image` — mission / fleet cards — wins); JSON-LD via `<JsonLd>`
   (`Article` + `BreadcrumbList` on reading and entity pages, `WebSite` + `Organization` on home).
5. **The staging mirror is noindex** (any build with a base path): no canonical, no hreflang.
6. **The gate.** `scripts/check-seo.mjs` runs in every `npm run build`: per indexable page one
   title (not the bare brand, ≤90), one description (≤160), self canonical, complete hreflang with
   built targets, og/twitter tags, JSON-LD that parses, one H1, no noindex; sitemaps = indexable
   pages; on the mirror, every page noindex.
7. **Mobile ships none of it.** `prune-streamed-assets.mjs` drops the entity pages and their
   `__data.json`, the sitemaps and the stubs (mobile build 75.6 MB of its 77 MB budget).

Amended 2026-11-09 with the operator's decisions on the open questions:

8. **Hub links in the footer.** Explore · Worlds · Catalog · Learn on every page, with the nav's
   own labels: the four hub pages were linked only from TV mode and the sitemap.
9. **HTML stays uncached at the edge.** Cloudflare caches `/_app/immutable` only; caching HTML
   would need a purge on every deploy, or cached pages point at deleted chunks. Revisit if
   Search Console shows slow time to first byte.
10. **Search titles beside poetic headings.** Essays, programs, science sections and weak science
    articles carry `seo_title` / `seo_description` in their overlays (14 locales); `<title>`,
    og and the meta description use them, the visible H1 and JSON-LD keep the poetic title.
11. **Every hub links all its entity pages in the prerendered HTML.** `/missions` and `/fleet`
    prerender a collapsed A–Z list at the page foot (`EntityIndex`, server load, no client JS cost).
    On the scene routes (`/moon`, `/mars`, `/venus`, `/explore`) the links live in the INDEX panel
    (UXD-015, 2026-11-12: the separate A–Z tab is gone): the panel is always in the DOM, hidden
    while closed, and before the sites load it is the plain list of every entity page from the
    route's server load; once loaded, each row whose object has a page carries a real link.
    Panels open on a click, which crawlers don't make, so the links are in the markup, not behind
    the click. `tests/e2e/index-links.spec.ts` checks the static HTML of every hub. (Amended
    2026-11-12, UXD-017: `/explore` has the same INDEX on all eight scales, one component
    (`ScaleIndex`); its eight lists are all in the one prerendered `/explore` HTML, hidden unless
    on screen, the rows with a page as plain links and the rows without one added on hydration.
    Explore's moons are rows of the solar-system list, not separate link rows.
    `tests/e2e/scale-index.spec.ts` checks the HTML and every scale.)
12. **Thin-page regression floor.** All entity pages stay indexable; thin ones are enriched from
    localized data the panels already show or the data files hold (linked missions with their
    one-liners, sites, crew, museums, related hardware, orbit and size figures, science sections,
    a lab formula's dials, defaults, worked result and assumptions) — no new prose.
    `check-seo.mjs` then fails an entity page whose `<main>` text is under its locale's
    character floor (`THIN_MIN_CHARS`). Characters, not words, because words are not a unit
    that holds across languages; per locale because the same content is ~1.1-1.2x the English
    length in the Latin / Cyrillic locales, ~1.0x in hi / ar and ~0.55-0.6x in zh-CN / ja / ko.
    Each floor is 95 % of that locale's thinnest page after the enrichment (en-US 350,
    zh-CN 175), so it guards against regressions rather than judging content;
    `CHECK_SEO_FLOORS=1 node scripts/check-seo.mjs` re-measures it.

Amended 2026-11-12 with the deep levels (operator: every deep type gets entity pages; stars and
their exoplanet hosts first; brief `docs/wip/2026-11-12-deep-entity-pages-brief.md`):

13. **Stars are entity pages, typed under `/explore/stars/<id>`.** One page per named star (62)
    and per exoplanet host (11, seven of which are named stars): 66 pages × 14 locales. The four
    host-only stars (`trappist-1`, `51-pegasi`, `toi-700`, `kepler-16`) are built from the
    system record. The typed path keeps a star id from ever meeting a planet, moon or small-body
    id (`getEntityIndex('explore')` lists only single-segment ids), and `getStarEntity`
    (`$lib/data/star-entity`, server-only) is keyed by star id alone. **An exoplanet system is a
    section of its host's page** (`#system`, each planet an anchor with its overlay text and
    data rows, culture doors included), not a URL of its own. Text is what the panels already
    show (the star and exoplanet overlays, catalogue values, culture doors, the H–R article
    link): no new prose. The page links back into the scene with `/explore?goto=<id>`, or
    `/explore?system=<id>` for a host-only star, and each planet with `?system=&planet=`.
    The thin-page floor (item 12) is unchanged and applies to these pages; a rendered measure of
    all 66 clears it in every locale.
14. **The scale INDEX is the crawl path; there is no list page.** Each INDEX row carries a `↗` link
    to its page (30 px on a fine pointer, 44 px on a coarse one). `/explore` renders the INDEX of
    every scale, hidden unless on screen, with its rows from the server load
    (`getScaleIndexRows` in `$lib/server/entity-index`, which names every row as its page does), so
    the prerendered `/explore` HTML links every body, star and black-hole page. (Amended
    2026-11-12, UXD-017: the first cut had a star INDEX at the neighbourhood and a body INDEX at the
    solar system; both are now `ScaleIndex`, and the six other scales have the same one.)
    Star and black-hole pages are reached like planets: from the INDEX of the scale they belong
    to, with the crumb back to `/explore`. (Amended 2026-11-12: the `/explore/stars` and
    `/explore/black-holes` list pages of the first cut were removed, operator: stars and black
    holes are members of the scale INDEX, not hub cards or lists of their own.) The mobile build
    prunes every star page with its `__data.json` (item 7).
15. **Remaining deep types.** The Local Group and the outer shells, and the Milky Way pins, get
    typed pages of their own once each entity's text clears the floor (the brief's measure:
    galaxies do not yet; deep-sky objects now do, item 17). Where the text is missing it is
    researched with cited sources, reviewed and translated by hand before the page ships; no page
    is shipped on a shared generic paragraph. Until then they stay INDEX rows that open their
    panels: since UXD-017 every one of them has its row in the INDEX of its scale before it has a
    page, and the page, when it ships, is one `href` on that row, no new UI. Black holes were the
    first of these to ship (item 16), the deep-sky objects with text the second (item 17).
16. **Black holes are entity pages, typed under `/explore/black-holes/<id>`.**
    Four pages (`sagittarius-a-star`, `m87-star`, `cygnus-x-1`, `gargantua`) × 14 locales,
    built by `getBlackHoleEntity` (`$lib/data/black-hole-entity`,
    server-only). The text is the researched, science-reviewed `fact` and `bio` of
    `docs/wip/deep-text/batch-01.md` in `i18n-src/<locale>/universe/black-holes/<id>.json`,
    translated by hand into the 13 other locales with the glossary forms of
    `native-terms.json`, plus the `discovery` line (English-only in the data file until now),
    which the panel shows in the reader's language too. The sources are in
    `static/data/text-sources.json` (ESO eso1907 and eso2208, NASA Science, Miller-Jones et al.
    2021, the DNGR paper, Thorne's APS interview, the GRAVITY 2022 mass) and on `/credits`.
    The page shows mass, distance and Schwarzschild radius of the three real holes and no spin
    (no source for any of the three); M87* takes the EHT image already in the repo as its hero.
    Mass and distance are the published values (GitHub #658): GRAVITY Collaboration 2022 for
    Sgr A*, EHT Collaboration 2019 paper VI for M87*, Miller-Jones et al. 2021 for Cygnus X-1,
    each row names its paper with a link, and a "Data sources" section lists the papers (ADS
    bibcode links) and the object's SIMBAD page (`scripts/refresh-black-hole-catalogue.mjs`).
    **Gargantua is fiction**: a visible badge (`bh_fiction_badge`), dashed and muted rather than
    in the accent colour, no figure at all (its mass, distance, spin and radius are model
    parameters with no source), nothing styled as a measurement. The row of Gargantua in the INDEX
    is dashed and muted the same way. M87*'s distance is the EHT
    paper's adopted 16.8 Mpc, 54.8 million light-years (ESO's eso1907 round figure, 55 million, is
    the same distance; Cosmicflows-4 gives M87 55.0 million, noted in the data). The pages link back with `/explore?bh=<id>`; the
    rows of the black holes carry the `↗` link (item 14's pattern), each in the INDEX of the scale it
    belongs to (UXD-017: Sagittarius A* and Cygnus X-1 in the Milky Way, M87* in Virgo, Gargantua,
    fiction, in a "Fiction" section at the foot of the Cosmic web), the pages
    are in the sitemaps, and the mobile build prunes them (item 7). The thin-page floor (item 12)
    applies unchanged; a rendered measure clears it in every locale.
17. **Deep-sky objects are entity pages, typed under `/explore/deep-sky/<id>`** (amended
    2026-11-12, operator: all eight recommendations of `docs/wip/2026-11-12-deep-sky-pages-brief.md`
    approved). One page per deep-sky object **with reviewed text**: the set is the ids of
    `i18n-src/en-US/universe/deep-sky/*.json` that are objects of `deep-sky-objects.json`
    (`deepSkyPageIds()` in `scripts/site-routes.mjs`), 120 of 141 today, × 14 locales = 1,680
    pages. The files decide: a text batch (the other 21, all photo-backed) adds its pages by adding
    its overlay files, with no code change, and `validate-data` requires each overlay in all 14
    locales with a `fact`, a `bio` and one or two links. Built by `getDeepSkyEntity`
    (`$lib/data/deep-sky-entity`, server-only): the catalogue record, the locale overlay (en-US
    fallback), the culture doors (M13, the Arecibo message) and, for a photographed object, the
    gallery telescope, caption and credit; an object with no overlay has no page. **One real
    object, one page, under the deep-sky id** (the only id with a record, an overlay, a photo and
    catalogue sources): the Milky Way globulars (`m3 m4 m5 m13 m15 m22 m92`) and the Local Group
    members `m32` and `m110` carry that id already, and `DEEP_SKY_ALIAS` (`andromeda → m31`,
    `triangulum → m33`, `omega-centauri → ngc-5139`, the last linked once ngc-5139 has text) names
    the others; their INDEX rows (UXD-017) link the same page and are named as the page names it.
    No second page, and no Milky Way or Local Group page for an object that has none (the other
    members stay INDEX rows). **Title** (brief Q5): designation, then the common name where the data
    has one (`M13 · Hercules Globular Cluster`, `M3 · NGC 5272`, `NGC 1365`); the data name is
    English in every locale and 88 of 141 are a bare OpenNGC code, so `deepSkyTitle`
    (`$lib/explore/deep-sky-title`) spaces the code and does not repeat it; the page H1, the `<title>`,
    the panel title and the INDEX row are that one string. The page shows the distance (from
    `dist_ly`, two significant figures from 10,000 ly up, the locale's number format and unit,
    `deepSkyDistance`), the V magnitude where there is one, the telescope of a photographed object and the
    constellation spelled out, each catalogue value linked to its source, the Data sources block
    (#658), the culture door, the overlay's learn-more links, the `gatewaySystem` link to the star page
    (`/explore/stars/<host>`), the gallery link and the credit of a photographed object, and the link
    back into the scene, `/explore?deepsky=<id>`. The panel and the page use the same formatters
    (`src/lib/explore/format.ts`). **Select = focus (UXD-019) for every object**: before this item only
    an object with a photo or a culture door opened its panel from `?deepsky=`, the INDEX or the canvas,
    and the other 96 with text were a highlighted dot; `enterDeepSky` now opens the flat panel, rings
    the glint and turns the camera to every one (a photo-less object has no approach warp and no hero).
    The pages are in the sitemaps and the mobile build prunes them (item 7). The thin-page floor
    (item 12) applies unchanged. The page has no hero image yet: heroes come with the B3 hero loader.

## Consequences

**Positive.** 12,138 indexable pages (was 3,892; items 13–14 add 924: 66 star pages × 14; item 16 adds 56: four black-hole pages × 14; item 17 adds 1,680: 120 deep-sky pages × 14, so 13,818 with it), each with its own text, title, description,
share card and structured data; every entity reachable by a stable URL in its reader's language;
regressions fail the build instead of surfacing in Search Console weeks later.

**Negative.** The web build grows by ~212 MB of HTML + `__data.json` and the prerender by a few
minutes; the staging (GitHub Pages) publish carries it too. Some entity pages stay short where the
data is thin; after the enrichment the shortest is 369 characters in en-US (`lab/weight`) and
27 of 8,303 were still under the old 80-word floor (mostly ko / sr-Cyrl, whose words are
shorter or longer than English ones). Two views of every entity now exist; a
change to what a panel shows should be mirrored on its page.

**Neutral.** The panels do not link to the pages (decision 11 links them from the hubs instead);
program rosters keep their `?id=` links into the 3D views.

## Alternatives considered

- **Make the `/c/*` stubs indexable.** They redirect humans away instantly (Google treats that as
  a doorway / soft 404) and are en-US only. Rejected.
- **Render the panels server-side on the hub routes** (`/missions?id=` as one URL per entity).
  Query-string variants of one route are weak canonicals, and the hubs are 3D / client-heavy
  pages. Rejected.
- **Hand-written SEO copy per entity.** ~8,000 pages × 14 locales of new prose is a translation
  programme, not a change; the existing overlays already carry the text. Deferred: per-page SEO
  titles beside the poetic H1s of essays / programs / science need the operator's per-page yes.
- **A dedicated JS route list for Lab formulas generated at build.** A new build step for 65 ids;
  the guarded JSON file is smaller and fails loudly when it drifts.
