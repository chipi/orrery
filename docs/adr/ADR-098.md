# ADR-098 — Per-locale UI message catalogues

> Status · Proposed · 2026-11-27 · operator go on the direction ("sounds like a good idea and well
> aligned with how the rest of things work"); the design below is the session's proposal

## Context

The UI strings (`messages/<locale>.json`, 3,817 keys) compile with Paraglide 2.21 in its default
`message-modules` output: one module per message, and each module holds the message in **all 14
locales** behind a runtime `if (locale === …)` chain. Tree-shaking keeps only the messages a route
uses, but every kept message carries 14 languages. A visitor reads one.

Measured 2026-11-27 (`SENTRY_SOURCEMAPS=1 npx vite build`, brotli, the minified bytes of each chunk
attributed to its source modules through the sourcemaps):

| Static JS | total KB | paraglide messages KB | share |
| --- | ---: | ---: | ---: |
| shell (root layout + entry) | 189 | 41 | 22 % |
| /explore | 559 | 260 | 46 % |
| /moon | 448 | 165 | 37 % |
| /fly | 458 | 135 | 29 % |
| /missions | 139 | 85 | 61 % |
| /fleet | 108 | 50 | 46 % |

One locale's whole catalogue is 84 KB (en-US) to 97 KB (de) brotli as JSON.

Everything else the client reads per locale is already split: the content overlays are per-locale
and per-chunk bundles fetched at runtime (`scripts/build-i18n-bundles.mjs`,
`src/lib/data/i18n-chunks.js`), the Lab's message tables are one dynamic import per locale
(`src/lib/lab/t.ts`), the glossary is one file per locale. An audit for other all-locale payloads
found one small one: `src/lib/name-origins.js` (15 KB raw, the launches pages).

What was tried or ruled out:

- **`experimentalMiddlewareLocaleSplitting`** (tried before, notes in `vite.config.ts`): works only
  without client-side routing; SvelteKit navigations failed with
  `globalThis.__paraglide.ssr.<key> is not a function`.
- **`experimentalStaticLocale`** (measured 2026-11-27): set to `"en-US"`, the route sizes did not
  move. The message modules read the locale from an imported binding, which the minifier does not
  fold, so all 14 branches stay. Paraglide's intended use is one full build per locale with the
  server picking the build: 14 builds and a different deploy.
- **`outputStructure: 'locale-modules'`**: one module per locale, statically imported; Paraglide's
  own docs say it tree-shakes worse.

## Decision

Keep Paraglide as the compiler and the `m.<key>()` call sites as they are. Add a build step that
turns its output into **per-locale catalogue chunks loaded at runtime**, the way the content
overlays already work:

1. **Catalogues.** For each locale, emit the compiled message functions of that locale only, grouped
   into chunks: `core` (the messages the shell and most routes use) plus one chunk per route area
   (explore, fly, surface, plan, missions/fleet, science, lab, …). The assignment is computed at build
   from where each message is used (the route closures in the Vite manifest), not by key prefix: a
   message used by two areas goes to `core` or to both, by size.
2. **Stubs.** The module `$lib/paraglide/messages` resolves to generated stubs with the same names and
   signatures: `sky_enter(inputs, options)` looks the function up in the loaded catalogue for the
   current locale (or `options.locale`). A stub is a few bytes, so tree-shaking per route still
   applies.
3. **Loading.** The client root `+layout.ts` load awaits the current locale's `core` chunk and the
   chunks the route needs (a generated route → chunks table) before the first render, and a
   navigation awaits the next route's chunks the same way. A locale switch loads the new locale's
   chunks before it re-renders. Chunks are content-hashed JS modules, so the service worker and the
   CDN cache them like any other chunk.
4. **Server.** Prerender and SSR keep Paraglide's all-locale modules (server bundles are not shipped
   to visitors), so the HTML is unchanged.
5. **Guard.** A stub called for a message whose chunk is not loaded is a bug: in dev it throws with
   the key and the missing chunk; in prod it falls back to the en-US string and reports once to
   GlitchTip. A unit test runs every route's message usage against its chunk table.
6. **Budget.** `check-route-budget` counts a route's catalogue chunks for one locale (the largest
   locale), like the per-locale Lab tables.

`name-origins.js` gets the same treatment in the same pass: one table per origin locale, loaded with
the launches pages.

## Consequences

Positive:

- Each route ships its messages in one language instead of 14: the estimate is −35 to −45 % of the
  static JS on the big routes (/explore about −240 KB, /moon −150, /fly −120, /missions −75) and
  about −35 KB on the shell.
- The same pattern as the content overlays and the Lab tables: one way to load translated text.
- Route budgets can come down by those amounts, which removes the pressure that pushed 3D modules
  into lazy chunks.

Negative:

- A generated layer between Paraglide and the app: a compile step, a stub module and a route →
  chunk table to keep in step with Paraglide upgrades (pinned; the step's tests cover the output
  shape it relies on).
- Navigation waits for the next route's catalogue chunk if it is not cached (one small request; the
  route's own JS chunks already load the same way).
- A first visit that lands on a small page loads `core` for its language. `core` is sized by the
  build and measured against the shell budget.

Neutral:

- Call sites, the message JSON files, the translation workflow and the term tools do not change.

## Alternatives considered

- **One whole catalogue per locale** (84–97 KB) loaded by the root layout: simplest, but every first
  visit pays the whole catalogue; small pages get heavier than today.
- **Fourteen builds** (`experimentalStaticLocale`): the ideal bytes, 14× the build time and a
  per-locale deploy.
- **Leave it**: the routes keep carrying 13 unused languages, and new UI keeps growing them 14×.
