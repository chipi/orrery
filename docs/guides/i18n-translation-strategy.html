Orrery translation strategy ​

How Orrery is translated, why, and how to do the next round. v1 · 2026-10-17

Read this before any translation work: a new language (Hebrew next), a new content surface, or a clean-up pass. The i18n style guide is the per-term brief for translators; this document is the thinking behind it, the decisions with their dates, the tools, the order of work and the mistakes already made so they are not made again.

1. What makes this project hard to translate ​

Orrery is physics, orbital mechanics, astronomy, space history and real hardware, in 14 locales (en-US source + es fr de pt-BR it nl zh-CN ja ko hi ar ru sr-Cyrl). A typical sentence mixes four kinds of words that each follow a different rule:

KindExampleRule (§3)
Ordinary prose"the probe slowed down"translate
Science, geography, astronomy termsMars, Hohmann transfer, Sea of Tranquility, Betelgeuse, LEOnative, as that country's universities write it
PeopleKepler, Gagarin, Neil Armstrongnative form of the name in that language
Vehicles, missions, agencies, companiesApollo 11, Soyuz MS-24, Chang'e 5, NASAEnglish everywhere, except the origin language uses its own name

The volume is large (counted 2026-10-17): 992 overlay files per locale (13,966 across all locales, i18n-src/<locale>/**) holding 10,047 non-empty string fields, plus 3,168 UI messages (messages/<locale>.json).

2. Where the text lives ​

  • UI strings — messages/<locale>.json, Paraglide (m.key()), compiled by npm run i18n:compile. ADR-017, ADR-031.
  • Content overlays — i18n-src/<locale>/<surface>/…json, shallow-merged over the language-neutral base data; bundled per locale into static/data/i18n/<locale>.json by scripts/build-i18n-bundles.mjs (ADR-079 D2). validate-data requires every en-US overlay file to exist in every locale.
  • Search — static/data/science-index.<locale>.json per locale (npm run build-science-index); the English title stays in the haystack so English terms still find a section.
  • Per-locale data that code reads — e.g. getVenusSites(locale), rover traverse stop labels, galaxy labels (galaxy_name_* messages): where a scene draws text from data, the data needs a locale overlay and the loader a locale argument.

3. The rules (operator decisions) ​

3.1 Names of things people built — origin rule (2026-10-17) ​

Missions, spacecraft, rockets, upper stages, stations, modules, programs, systems, agencies, companies, design bureaus: English in every locale, except the locale of the name's origin, which uses the original name.

  • Russian/Soviet in ru: «Союз МС-24», «Мир», «Протон-М», «Курс», НПО им. Лавочкина.
  • Chinese in zh-CN: 神舟, 天宫, 嫦娥五号, 朱雀三号.
  • Japanese in ja, Korean in ko, Indian in hi (श्रीहरिकोटा), Iranian names in Arabic script in ar, a Serbian name in sr-Cyrl, an Israeli name in he.
  • Everywhere else: Soyuz MS-24, Mir, Shenzhou.
  • Agencies have a local and an international name (operator, 2026-10-18). Every other language keeps the international one: "NASA should be NASA — this is not translation, it's replacing words" (operator, 2026-10-17). The agency's own language uses the local name, as its own Wikipedia writes it (2026-10-18): hi इसरो (67 vs ISRO 6), ru Роскосмос, zh-CN 国家航天局 (CNSA 0), ar مركز محمد بن راشد للفضاء (MBRSC 0). ja keeps JAXA (50 vs 宇宙航空研究開発機構 9). When unsure, give both: इसरो (ISRO). native-terms.json class agency; the one exception is a list of English search terms in sourcing/gaps.json, quoted as typed.
  • Russian running text puts vehicle names in «» quotes; headings don't.
  • In Cyrillic text (ru, sr-Cyrl) a name kept in Latin script never takes a case ending, with or without a hyphen (no "NASA-ин", "Voyager-а"). A common noun before it carries the ending: ru агентства NASA, аппарата Voyager 2; sr агенције NASA, летелице Voyager 2; or the sentence is reworded (decided 2026-10-18 at the operator's request: Russian press usage, and one rule for both languages; the Serbian Pravopis was not checked). Native-script names inflect normally (Кеплера, Ориона). Latin-script languages keep their own standard forms (German genitive NASAs).
  • Code: ORIGIN_NAMES, nativeName(), nativeCompound() in src/lib/name-origins.js. Every origin name must be listed there, or the checker rejects the native form and the scan cannot find leftovers.

3.2 Science, geography, astronomy, people — native everywhere (2026-10-17) ​

"You don't go to a Russian university and use English words in science for planets, orbits… The same is for any country." Terminology is written the way that country's universities, schools and space agency write it:

  • planets, moons, small bodies (Марс, 火星, बृहस्पति, यम);
  • eponymous terms (законы Кеплера, сфера Хилла, эффект Оберта, пояс Койпера);
  • term abbreviations (НОО / ГСО / ВКД for LEO / GEO / EVA);
  • Moon and planet surface features (Море Спокойствия), stars, constellations, galaxies (Бетельгейзе, галактика Андромеды);
  • geography (countries, cities, oceans, regions);
  • people: every language has its own form (Кеплер, ケプラー, 开普勒; de "Juri Gagarin", fr "Iouri Gagarine").

Exceptions only where an international standard really sticks out in that language's own sources (instrument acronyms like JWST; Latin IAU names where native sources use them). ISS is a term, not a name (operator 2026-10-18): "МКС is the Russian abbreviation of Международная космическая станция." Each language uses its own abbreviation or name for the International Space Station, as native-terms.json records it, checked against each language's own Wikipedia intro (2026-10-18): ru МКС, sr-Cyrl МСС, es EEI, pt-BR EEI, it SSI ("in sigla SSI"), hi आईएसएस, zh-CN 国际空间站, ar محطة الفضاء الدولية; ISS where the language's own sources write ISS (de, fr — SSI there is mostly Canadian — nl, ja, ko).

3.3 One thing, one name per language (2026-10-17) ​

"We don't want to have in one language the same thing in three places, in three different ways." Within a locale every vehicle, program, person, body or place is written the same way everywhere it appears.

  • The canonical form is the one on its own page — the gallery and entity pages: fleet (launchers, spacecraft, stations, landers, rovers, suits, engines), programs, missions, planets and small bodies, sites, assets. Their name / short_name fields in i18n-src/<locale>/… set it.
  • Pass 1 — the pages themselves: make those name fields follow §3.1 / §3.2.
  • Pass 2 — the text around them: every mention inside editorials, essays, science articles, program stories, descriptions, captions and notes (the body text, not just titles) uses the canonical form, inflected by grammar where the language needs it.
  • Check (to build): for each entity, its canonical form per locale, then every other spelling of it in that locale's text — the English name where a native one exists, a transliteration, an older variant (ja ネプチューン next to 海王星).

3.4 Other standing rules ​

  • Universal symbols stay as symbols (Δv, Isp, C₃, g, SI units) — style guide §1.
  • No native-speaker review step; the operator reads the Serbian personally.
  • No paid model run without a size + cost estimate and an explicit go.
  • Free route first (operator 2026-10-18): fixes are proposed as hand edits, the local scripts, or in-session subagents. A paid API run is mentioned only when asked for, or when no free route can do the job, with the reason.
  • Fix what a pass finds in the same pass; hand-edit rather than re-run a model.

3.5 Names go through the glossary, never straight into text (operator 2026-10-18) ​

Hand-writing a native name into one string, without the glossary, creates drift: the next pass, the next locale and the next page do not know it. So:

  1. Glossary first. Every proper name (person, place, feature, body, star, facility) that gets a native form goes into scripts/i18n-tools/native-terms.json in all thirteen locales before any text uses it. Text is then written by glossary-apply.mjs (read and corrected per locale), not typed into one file.
  2. The site's existing form wins. Before choosing a form, list how every locale already writes the name everywhere (overlays and messages/). The entity page's form is canonical (§3.3); with no page, the form most of the site already uses. A new spelling is chosen only where the site has none.
  3. Prove it after every pass. For each name touched: no English key left in a non-Latin locale's text, and no second spelling in any locale. A pass is not done until that check is clean.
  4. No extra spend for self-made problems. Repairs to an agent's own drift are done in session by hand or by the scripts, never with a new paid run.

4. How to decide a form you are not sure of ​

Search the term in the target language and read how native pages write it — the national space agency, universities and school textbooks, the national Wikipedia. Use that form. It can differ per language; check each one.

Record the source in scripts/i18n-tools/native-terms.json → sources. Example (Hindi, 2026-10-17): NCERT class 6 writes the outer planets अरुण, वरुण, यम (प्लूटो), so the glossary uses those over the transliterations यूरेनस / नेपच्यून / प्लूटो already in the text.

5. The glossary and the tools ​

  • Glossary — scripts/i18n-tools/native-terms.json: native form per locale for each term or person, by class (body first; people, features, stars, abbreviations to follow). It is the single answer to "how is X written in language Y".
  • Checker — problems(locale, en, out) in scripts/lib/translate-quality.mjs (also NAME_POLICY, appended to every model prompt). Every writer runs it on each new string; an edit that adds a failure is refused. scripts/i18n-guard-replay.mjs replays all checks over the whole corpus — run it before and after changing a check.
  • Coverage scan — scripts/i18n-coverage-scan.mjs: missing files/keys, empty, identical to English (incl. Title-Case titles), placeholders, origin names left in English (nativeNameMissing). SAME_OK lists strings identical on purpose.
  • Editing kit — scripts/i18n-tools/ (README there): generate candidate edits, review them line by line (showdiff.mjs), apply with checks (apply-edits.mjs, apply-literal.mjs, apply-keys.mjs). Hand-written inputs and analysis results are versioned under scripts/i18n-tools/maps/<date>-<arc>/ — reuse and extend them; never keep them only in a temp folder.

6. Order of work for a new language (e.g. Hebrew) ​

  1. Agree the outcome per data set first with the operator, then execute one by one with progress reports.
  2. Add the locale (Paraglide project settings, LANGUAGE_NAMES, LOCALE_RULES in translate-quality.mjs, RTL handling like ar).
  3. Glossary column first: fill the new locale in native-terms.json for every class, checking unsure forms on native pages (§4). Add the language's origin names to ORIGIN_NAMES (Israeli missions and satellites: Beresheet → בראשית in he).
  4. Size the run (field count × cost) and get a go before any paid translation; the prompt carries NAME_POLICY but not the glossary: run glossary-apply.mjs on the output.
  5. Translate UI messages, then the gallery and entity pages (their names become the canonical forms, §3.3), then the editorial and article text, using those forms.
  6. Gate: validate-data, guard replay (no new rejections), coverage scan (sameAsEnglish, nativeNameMissing both 0), npm run test:coverage, and look at the routes in a browser.
