# PRD-027 · Museums: where the real hardware is on display

> Status · Accepted 2026-10-22 (option A); rewritten the same day, replacing the never-built 2026-06-09 "/science visit-list" draft
> Date · 2026-10-22
> Owner · Marko
> Closes into · #617 (museum button) and the museum epic it grows into
> Builds on · PRD-036 (collectible cards) · the launch-site pattern (`static/data/fleet/launch-site/*.json` → `src/lib/earth-launch-site-adapter.ts` → /earth markers) · PRD-028 (sister: ground observatories)

> **Why this is a PRD.** It adds a new kind of entity to Orrery. Museums become things with a place on the globe, a detail panel and a collectible card, and every spacecraft page gains a way to go and see the real one. That touches data, /earth, cards, translations, analytics and e2e, so the shape is agreed before code. The 2026-06-09 draft was a hand-written list page; this replaces it.

## 1 · What

1. **Museum entries.** One data entry per museum that has at least one real Orrery object on public display: name, city, country, latitude/longitude, official website, and the objects it holds.
2. **"See it in a museum" button** on the page of every object that is on display (fleet object panels, `/science/history` pages). It opens the museum's official website in a new tab.
   - One museum: the button links straight to it.
   - Several museums: the same button opens a small menu listing every museum (name + city), each opening in a new tab. Ordered by country, then city, so no museum is favoured. Keyboard and touch accessible.
3. **Museums on /earth.** A "Museums" marker layer beside the launchpads, from the same adapter pattern launch sites use. Tapping a marker opens the museum panel.
4. **Museum panel and card.** Each museum has a detail panel (where it is, what real Orrery objects it holds, each linking to its object page, and the official website) and a collectible card like every other entity (PRD-036).
5. **A museum list.** One page listing all museums (by country), so they can be browsed without the globe. This is what the 2026-06-09 draft's `/science/visit-list` was for.

## 2 · Rules for what counts (operator, 2026-10-22)

- **Real objects only.** An object gets a museum link only where the flown article or a real flight backup / spare is on public display. Replicas, mock-ups and models get no link, so the button never leads to a model.
- **Any museum in the world**, not only ones the operator visited.
- **A museum is in** when it displays at least one real object that Orrery has a page for. Visitor centres at working space facilities count when they display real hardware (e.g. JPL, Space Center Houston).
- **Evidence for every link.** Each object ↔ museum row carries a source showing the object is on display there now, preferably the museum's own collection page. Museums move and loan objects (Apollo 11 *Columbia* toured 2017–2021), so the source must be current, not historical.
- **The operator ticks every row** before it goes live.
- **The links live once, on the museum entry.** Object pages derive their button from the museum entries, so the two sides cannot disagree.

## 3 · Data shape (proposal)

```ts
type Museum = {
  id: string;              // kebab-case, e.g. 'nasm-washington'
  name: string;            // English; translated forms via the glossary (§5)
  city: string;
  country: string;         // ISO 3166-1 alpha-2
  lat: number;
  lon: number;
  website: string;         // official site, https
  credit: string;          // hero image credit, same rules as every gallery
  holds: Array<{
    ref: string;           // fleet id or '/science/history/<slug>'
    item: string;          // which one, e.g. 'Command module Columbia (flown, Apollo 11)'
    kind: 'flown' | 'backup';
    evidence: string;      // URL showing it is on display there
    checked: string;       // date the evidence was read, YYYY-MM-DD
  }>;
};
```

`validate-data` gains a check: every `ref` resolves, every URL is https, every row has evidence and a date, and no `kind` other than flown/backup.

**Decided (operator, 2026-10-22): option A.** Museum entries are a fleet category `museum` (`static/data/fleet/museum/*.json`), like `launch-site`; the /fleet catalogue browser leaves the category out.

| Option | For | Against |
|---|---|---|
| **A. A fleet category `museum`**, like `launch-site` (chosen) | Panel, card, gallery, translation overlays, alt texts and the /earth adapter already exist for fleet categories; launch sites prove a place can live there | "Fleet" is a hardware catalogue; a museum is not hardware, so the /fleet browser shows an odd category unless it is filtered out there |
| **B. A new entity type** with its own data folder | Clean semantics | Every pipeline (panel, card kind, overlays, alt texts, sitemap, share stubs) has to be wired again; several times the work |

## 4 · Images

Each museum card and panel needs a hero photo with a usable licence (the building or its hall). Sourcing goes through the curated fetch scripts (Commons first; native-language sources first for non-US museums), with per-image operator approval and the usual alt text in 13 locales. A museum without an approved hero shows the panel without a card until one is found.

## 5 · Names and translations

- **Button and menu labels, panel and list chrome:** translated by hand into the 13 locales (free route).
- **Museum names:** follow the origin-language rule for institutions: the museum's own name in its own language's locale (Мемориальный музей космонавтики in `ru`, 中国科学技术馆 in `zh-CN`), English elsewhere. Entered in `native-terms.json` first, before any text uses them. City names follow the places rule (native in every locale).
- **Object descriptions in `holds.item`:** translated like other short data strings.

## 6 · Measurement

- `outbound` Umami event on the museum button and menu items, target `museum`, plus the museum id.
- Card opens and shares ride the existing card events (PRD-036).

## 7 · Steps

1. **Research (in-session, no paid run).** Every fleet entry (~290: crewed spacecraft 28, suits 13, launchers 38, engines 22, landers 27, rovers 13, orbiters 54, …) and the 4 history pages: which museums display the real one, flown or backup, with evidence. Most entries will have none (still flying, lost, on another world). The 2026-06-09 candidate list (about 29 places: 21 museums, 4 facility visitor centres, 4 launch sites; in this file's git history) is the starting point, not the limit.
2. **Table to the operator:** museum · object · flown/backup · evidence · official site. The operator ticks rows.
3. **Build:** data + validation, the button and menu, the /earth layer, panel, card, list page, translations, analytics.
4. **Images:** sourced and approved per museum (§4); can trail step 3.

## 8 · Done

- Every ticked row renders: the button on the object page, the object on the museum panel.
- `validate-data` green with the new museum checks.
- e2e: one object with one museum (direct link, new tab), one object with several (menu), one museum marker on /earth opening its panel, desktop and mobile.
- The button, menu, panel and list are translated in all 13 locales.

## 9 · Non-goals

- **Links to the operator's photo galleries** on airandspacehistory.com: split out to #618, after that site's rework.
- **Replicas and models**, however good (§2).
- Opening hours, tickets, reviews: Orrery is not a travel site.
- Launch-viewing and facility tours with nothing real on display (launch sites are already their own entities).
- Planetariums and observatories (PRD-028).

## 10 · Risks

- **Exhibits move.** Loans, tours and renovations. The `checked` date on each row makes staleness visible; a periodic re-check of the evidence links is part of maintenance.
- **Flown vs backup vs replica is easy to get wrong**, and museums don't always say. A row whose evidence does not state which it is stays out.
- **Coverage skews to the US and Europe**, where collections are documented online. Russian, Chinese, Indian and Japanese collections are searched in their own languages first.
