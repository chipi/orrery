```
S1 → S2a(freeze: i18n-keys, M4-selection, D13, D10, URL/version grammar; M1 renderers)
   → S2b ∥ S2c
   → S3 (codec+versioning · linear-DAG recompute · Notebook · Focus/a11y/mobile)   [XL, sub-split]

   → RELEASE EXIT gated by: built→goal coverage CI · S6 full tool surface · T4 quality
     (all three require Phase 2 substantially complete)

Start EARLY, parallel to Phase 1–2 (NOT at the end):
   INFRA-auth-spike → INFRA-lab-api ─┬─→ T4 (Door 1)
                                     └─→ MCP-auth (Door 2)     one identity layer, two doors
   S4 MCP scaffold (after S2a + 1 registered domain)
   T2 Canvas ∥ T3 generative (independent of each other; neither gates goals)
```

**The plan's original path was right up to ⛳M2, wrong after** — the release end is gated by
Phase 2 + the auth chain, not a fan-out that "just happens."

**Parallelism is ORDERING, not schedule compression (Fable-5 r5 MAJOR-3).** The delivery
model is one supervising operator reviewing step-by-step + a small number of agent lanes — not
infinite hands. The "∥" marks mean *"no dependency forces these to serialize, and the spike
must start early to de-risk,"* NOT "these run at zero wall-clock cost in parallel." Real
execution interleaves; the multi-month estimate assumes roughly 1–2 active lanes, not the
4 tracks drawn. Treat the graph as a dependency DAG for *ordering*, and size duration off the
serial critical path (S1→S2a→S3→Phase 2), not the width of the fan-out.

## 4b · Per-slice completion protocol (operator, 2026-08-29 — STANDING for the whole build)

A slice is not "done" when its code is written — it is **landed** only after this ritual,
run after every slice:
1. **All children committed + individually preflight-green** (each child gates on its own preflight).
2. **Fable-5 holistic review** of the *landed reality* (not the plan) — "did this slice land
   well: boundary honest, tests real, architecture sound, nothing quietly broken?"
3. **Address the review findings** inside the slice (don't defer).
4. **Full `npm run preflight` runs clean** on the whole slice together — stability check, not
   just per-child. Work out any instability *within the slice*.
5. **Full e2e when the slice warrants it (judgment, not mechanical).** `preflight` does NOT run
   e2e, so it can't prove the *running app* is unchanged. Run full Playwright on BOTH
   `desktop-chromium` + `mobile-chromium` (`--workers=1`) at **meaningful integration points**:
   a large structural refactor, any slice that touches the running surface (`/lab`, goals), and
   always before a push/tag. Contract-only / pure-internal slices lean on preflight + targeted
   tests. **S1 specifically gets full e2e at close** — it rewrites 200+ import sites, and e2e is
   the definitive "outer surface unchanged" proof unit tests can't give.
6. Only then is the slice landed. **No push** — that remains the operator's explicit gate.

Pre-slice Fable-5 rounds check the *plan*; this post-slice review checks the *reality*.

## 4c · S1.2 decision — interplanetary-geometry split DEFERRED to S2 (2026-08-29)

The manifest footnote 4 said "split `interplanetary-geometry.ts` at S1.2, or keep whole
app-side if fiddly." **Decision: keep it app-side for S1; do the split at S2.** Rationale:
the split is forced by the **provenance fidelity axis** (`computed` vs `replayed-published`,
A01.2a) — an **S2 contract that doesn't exist yet in S1**. `buildInterplanetaryTrajectory`
dispatches: analytic Tier-1 (via `mission-arc` primitives, `computed`) vs
`buildFromHelioWaypoints` (Tier-2 replay, `replayed-published`). Splitting the seam before the
contract that defines it = guessing; splitting at S2 (when `FigureSpec`/provenance land) is
when it has a real shape. S1.2 moves the unambiguously-pure transfer modules; app-side
`interplanetary-geometry` imports the now-kernel `mission-arc`. This invokes the manifest's
own documented fallback — sequencing refinement, not a scope cut; the split still happens (S2).
