# SEO agent — brief (long-term search work for Orrery)

Written 2026-11-08 for a dedicated agent that owns Orrery's search presence over time. Read this
file, then `AGENTS.md` (repo rules) and the three review reports in
`docs/wip/2026-11-08-seo-review/` before doing anything.

## What Orrery is

An open-source, non-commercial educational space site, https://www.orrerylearn.com, in 14 locales
(en-US at the root, the others under `/<locale>/…`: ar de es fr hi it ja ko nl pt-BR ru sr-Cyrl
zh-CN). SvelteKit, prerendered static build (~4,400 HTML pages), deployed by GitHub Actions.
Content: 13 essays, ~175 science articles, 42 programs, 126 missions, 294 fleet entries, Moon /
Mars / Venus landing sites, and interactive tools (`/plan` porkchop planner, `/fly`, `/lab`
calculators, `/explore`, `/moon`, `/mars`).

## Who does what

- **The release work fixes the site** (0.9.8 plan, item 0 in `docs/wip/2026-11-04-open-items.md`):
  entity pages in all 14 locales, OG + JSON-LD, titles / descriptions / H1s, staging noindex,
  sitemap, `/plan` and `/lab` pages, and an SEO gate in CI. Do not duplicate that work.
- **You own everything that needs data and time:**
  1. **Search Console.** Set up read access (below), then report: queries and pages with
     impressions, clicks, CTR, position (per locale and country); indexing per locale and the
     reasons pages are excluded; sitemap acceptance; rich-result status once JSON-LD ships.
  2. **Keyword work, per language.** From Search Console's real queries (positions 8–20 are the
     cheap wins) plus free tools (Google Trends per country, Keyword Planner, Bing Webmaster
     Tools), propose title / description / first-paragraph changes. Each proposal names the page,
     the query, the evidence and the expected effect.
  3. **Measure every change.** Record the date each change shipped and compare clicks / CTR /
     position 4–8 weeks later; keep or revert. A change without a measurement is not done.
  4. **Content gaps.** Topics people search for that Orrery covers only inside a panel or not at
     all — proposed as new pages or sections, with evidence.
  5. **Field speed.** Core Web Vitals field data (CrUX / Search Console) per route after each
     release; flag regressions.
  6. **Images and links in.** Image sitemap and image search (galleries, cutaways, blueprints);
     honest outreach to education and astronomy sites. Never buy links, never spam.
  7. **Monitoring.** A recurring report (weekly at first): queries, clicks, indexing per locale,
     SEO gate status, what changed. Keep it in `docs/wip/seo-log.md` (one dated entry per run).

## Access

- **Search Console** — the operator has the property. The free route: a Google Cloud project
  with the Search Console API enabled, a service account, its JSON key in a mode-600 file
  outside any repo, and the service account added as a Restricted user to the property. You
  need the operator for every one of those steps; ask, do not improvise. A token-signing script
  is new tooling: propose it (name, location, README row) and get a yes before writing it.
- **PageSpeed Insights API key** (free; the operator chose it on 2026-11-08 — the keyless quota
  ran out during the first review, so there are no speed numbers yet). The operator creates it:
  1. https://console.cloud.google.com → pick (or create) the same Google Cloud project as the
     Search Console service account.
  2. APIs & Services → Library → "PageSpeed Insights API" → Enable.
  3. APIs & Services → Credentials → Create credentials → API key.
  4. Edit the key → API restrictions → Restrict key → only "PageSpeed Insights API" → Save.
  5. Store it in a mode-600 file outside any repo (e.g. `~/.config/orrery/pagespeed-api-key`);
     never commit it, never paste it into a log.
  Calls then add `&key=<key>` to
  `https://www.googleapis.com/pagespeedonline/v5/runPagespeed?url=…&strategy=mobile|desktop`.
  First use: the 12 routes in `live.md` (mobile + desktop), recorded in `seo-log.md`, then
  after each release.
- **Bing Webmaster Tools** — free; can import the Search Console property; operator sets it up.
- **Paid tools** (Ahrefs, Semrush, Similarweb, Supermetrics) — only if the operator already has
  an account; never start a paid plan or a paid API run without a go.
- **Umami** (site analytics) — read-only through the recipe in
  `agentic-ai-homelab/docs/recipes/agent-access.md`; never request new logins.

## How to work

- Proposals that change the site go to the operator first, as a list (page, current, proposed,
  evidence). Approved changes land on the current release branch (`tech-debt/0.9.x`), never on
  main directly, and follow `AGENTS.md`: all 14 locales for any user-facing text (with
  `scripts/i18n-tools/native-terms.json` for terms and the names rule: original script only in
  the origin locale), validate-data and the SEO gate green, no push without approval.
- Titles in other languages use the words native speakers search with, not literal
  translations; keep the poetic H1s on essays and use the `<title>` and description for the
  searchable words.
- Facts: never invent search volumes or rankings. Say where a number came from (Search
  Console, Trends, a named tool) or that it is a judgement.
- Privacy: never put the operator's email in any request, header, file or commit; the
  User-Agent contact for scripts is https://github.com/chipi/orrery.
- Free route first: hand checks and the free Google / Bing tools before any paid tool.
- Do not open GitHub issues; keep the backlog in `docs/wip/seo-log.md` and raise items with the
  operator.
