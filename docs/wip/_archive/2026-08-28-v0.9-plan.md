# v0.9 plan — "The Physics Lab release"

Status: **PLANNING (semi-formalized)** · 2026-08-28 · operator-approved shape (all
tracks A–F + flagship are in v0.9; this doc fixes the *order*, not the scope).

Flagship: **Physics Lab + MCP server** (#458, PRD-033 / RFC-037 / UXS-015).
Everything else is a supporting track that either **gates**, **interleaves with**,
or runs **parallel to** the flagship.

---

## The one fact that drives the whole sequence

The flagship's first move — **S1: carve the physics kernel out of
`src/lib/orbital/`, `astronomy/`, `satellite/`, `lambert*`** — is a repo-wide move
of the physics modules into `src/lib/physics/`. **Anything still editing those
modules collides with the extraction.** So the sequencing question reduces to:
*what touches the physics modules or the shared chrome, and must therefore settle
before S1?*

Only three things genuinely gate the flagship start. Everything else is a clean
interleave or fully parallel.

## Phase 1 — the flagship spine (with two interleaves)

The internal slice order S1→S6 is fixed in RFC-037 §10. Two supporting items slot
in at specific points rather than before the whole thing:

```
S1 kernel boundary
S2 registry + FigureSpec + renderers
   └── [#308 geocentric Lambert porkchop] ← first EXTERNAL kernel consumer;
        proves the kernel API on /plan before the MCP server leans on it
S3 /lab — Notebook + Focus (v1 home)
S4 MCP server — private beta
   └── [#387 Caddy edge caching/header contract] ← define the edge contract
        JUST BEFORE the mcp. vhost, so hosting slots into a clean pattern
S5 Canvas + wiring + promote (T2)
S6 MCP OAuth 2.1 + full tool surface
```

- **#308 → after S1–S2.** Geocentric porkchop (Moon + planetocentric moons on
  `/plan`) is the ideal first external consumer of the extracted kernel — it
  validates the boundary/API on a real surface before S4's MCP tools depend on it.
- **#387 → right before S4.** Both #387 and the MCP server configure the VPS/Caddy
  edge. Define the caching + response-header contract first; the `mcp.` subdomain
  vhost then slots into an established pattern instead of inventing one.
